# Screen Agent v0.1.7 preview

Unsigned .NET 8 WPF companion for Windows 10 2004+ / Windows 11 x64. This prerelease wires device pairing, confirmed screen IDs, draw highlights, dictation and correction learning to Agent Desk. Windows desktop behavior and the live Desk integration still require the manual checks below.

Download `ScreenAgent.exe` and verify it against `SHA256SUMS`. Optional `tessdata.zip` contains eng+deu models: extract the `tessdata` directory beside the exe. WebView2 Evergreen Runtime is required; the Tesseract fallback also needs the Visual C++ 2015–2022 x64 runtime. The .NET runtime is bundled. The executable is about 210 MB; exact size/hash are measured by Windows CI. No trimming or installer.

## First run, in plain words

1. **Start `ScreenAgent.exe`.** Nothing opens on screen: no console window, no panel. The app lives in the notification area
   (bottom right of the taskbar; on Windows 11 the round icon may be hidden under the `^` arrow, drag it out to keep it visible).
   A balloon says so at start until the device is connected. Starting the exe a second time simply opens the Desk window of the running app.
2. **Connect the device.** Click the tray icon (or right-click, **Desk öffnen**). The Desk window opens as a normal window: it can be
   minimised, resized and moved, it is not always on top, and it remembers its size and position. Click **Im Browser verbinden**.
   Your normal browser opens. If asked, request a Telegram login link, open it, and click **Dieses Gerät verbinden**.
   The app takes over automatically and opens Desk signed in. Do not copy a code or device token. Closing Desk only hides it; the app keeps running.
3. **Start a session.** Press **Ctrl+Win+Shift** (Strg+Win+Shift; any key order, press and release once) or use tray **Sitzung starten**. A dialog started with the purple button in the Desk window also counts as a session.
   A small grey note in the bottom-right corner appears with the state ("Sitzung · 3 IDs"). It never takes focus, cannot be clicked,
   and fades when the mouse comes near. Press the keys again, or use the tray, to stop; the note disappears. The tray icon always shows
   the state: grey ready, green session, blue dictating or drawing, yellow paused, orange needs attention. Hover it for the exact text.
4. **If the note is orange** it tells you what to do. "Nicht verbunden" or "Desk nicht angemeldet" means step 2 is not done.
   "Desk-Stimme startet nicht" means the Desk page did not confirm that voice started within two seconds: open the Desk window from the
   tray, check that you are signed in and allow the microphone when asked.
5. **Quit** from the tray menu (**Beenden**). Voice stops and the screen context is cleared first.

**Wispr keeps working.** Ctrl+Win alone is Wispr's chord and the app does not touch it: it does not swallow it, does not inject a key
and does not react until a third key makes the chord. Only when Shift (or, for dictation, Alt+Win) completes one of our chords does the app send
one invisible neutral key (VK 0xE8) while Win is still held, so that releasing Win does not open the Start menu. Ctrl+Win+Alt (Wispr's command
chord) and every other chord that is not exactly one of ours pass through untouched. (One corner: if you press Alt and Win first and Ctrl only
afterwards, the app has already added its single mask key, because at that moment the chord looked like its own Alt+Win. Press Ctrl first.)
Use the LEFT Alt key: on German keyboards the right Alt is AltGr, which Windows reports as Ctrl+Alt. The app swallows only Caps Lock (while a
session is on, so a Caps tap or hold can mean "draw") and the M of Ctrl+Win+Shift+M (only while a session runs).
**What may still happen with Wispr:** Wispr starts listening on Ctrl+Win, before our Shift arrives. If you press the three keys within about
a tenth of a second Wispr is likely to discard such a short recording; if you hold Ctrl+Win and add Shift late, Wispr may have started and may type
a few words. This cannot be checked without the laptop; see the acceptance table.
If your `config.json` still holds defaults from v0.1.0 to v0.1.3 the app replaces them with the new ones at start (the old file is kept as
`config.json.v0.1.1.bak`) and says so in a balloon.

## Keys (defaults)

| Keys | What it does |
| --- | --- |
| Ctrl+Win+Shift (any order, press once) | Start the voice session (dialog, screen context, frames); press again to end it |
| Ctrl+Win+Shift+M | Mute / unmute the microphone, only while a session runs. The status note turns red ("Mikro stumm"), same state as the Desk dock button |
| Ctrl+Win+Shift+P | Pause / resume capture |
| Ctrl+Win+Shift+D | Show / hide the drawing panel, only while a session runs (the tray has **Zeichnung zeigen** at any time) |
| Alt+Win (hold 250 ms) | Dictate; release to transcribe and insert |
| Alt+Win+Shift (any order, press once) | Dictation on; press again to end it and insert the text |
| Alt+Win+Y | Hands-free dictation toggle (second way to the same) |
| Caps Lock (hold 200 ms, only in a session) | Draw magenta, 5 px strokes; letting go of Caps sends the drawing; tap (under 200 ms) = normal Caps Lock |
| Ctrl+Win+Shift+X | **Stop** the computer-control run at once (only while a run exists) |
| Ctrl+Win+Shift+Y | **Confirm** the question on the overlay (physical keys only; the same as saying the code) |
| Ctrl+Win alone | Not ours: Wispr Flow |

The tray menu lists every key, and each chord can be changed under `Hotkeys` in `config.json`. **Only the Caps Lock key draws** (it is the `draw` entry; Shift cannot be bound to it: action keys are Caps, Space, A–Z or F1–F12, and the log line `client.app` and the `hotkey.draw.*` events name the key). Shift is only a modifier of the session and dictation chords.

## Controls

- Ctrl+Win+Shift, then release without another key: toggle the screen and Desk voice session together (or tray **Sitzung starten/beenden**). The action happens when the first of the three keys is released. Missing voice acknowledgement after two seconds shows an orange note and tray text with the next step.
- Ctrl+Win+Shift+M while a session runs: mute or unmute the microphone through the Desk page (`window.__deskVoice.toggleMuted()`); no audio leaves the device while muted, the session continues. The small note turns red.
- Alt+Win held at least 250 ms: dictate; release to transcribe and insert. Adding Ctrl discards. Adding Shift latches it (same as Alt+Win+Shift).
- Alt+Win+Shift: dictation toggle. First press starts recording, the second ends it, transcribes and inserts. There is no length limit: long dictations are recorded to disk and sent in chunks while you talk (see “Dictation: recordings, long dictations, captions”).
- Alt+Win+Y: hands-free dictation toggle, as before.
- Caps Lock outside a session works normally. In a session, tap under 200 ms toggles normally; hold at least 200 ms to draw magenta strokes with the mouse, over any window or across several windows. The drawing ends when you release Caps, not before: you hold the key, draw as many strokes as you like, let go. At that instant the drawing layer stops catching the mouse (your next click reaches the window below), the picture is taken without the layer, the strokes are drawn into it in memory (magenta, 5 physical pixels wide whatever the display scaling), and the crop around the strokes (15 % margin) plus the whole screen go to the Desk as the highlight; the strokes fade over 1.5 seconds. Holding Caps without drawing sends nothing. If a highlight cannot be sent the note says why.
- Ctrl+Win+Shift+P or tray **Pause**: pause capture. The tray menu also has **Desk öffnen**, **Gerät trennen**, **Beenden** and shows the current status and the session key. Closing the Desk hides it; minimising puts it on the taskbar like any window. The Desk window opens only on your request (tray click, tray menu, starting the exe again) and never takes focus by itself.

During a session the small note (and the tray tooltip) indicates session, dictation, drawing, a locked screen and the confirmed ID count. OCR is local; registry-confirmed IDs, the foreground process name and the frame version reach the native screen endpoint (a# recognition stays on top).

## What the agent is doing, live (v0.1.7)

- **Activity rows.** Bottom right, above the status note: up to four small dark rows, one per tool call the voice agent makes (a purple dot while it runs, a green tick for 2.5 s when it is done, orange with the reason for 8 s when it failed). "Denkt nach …" / "Gehört …" is one short row that the first tool replaces. The app's own steps show up the same way, so typing the Main Agent prompt is visible from the first moment: "Main Agent · Prompt kommt an", "suche das VS-Code-Fenster", "Fenster gefunden", "Fenster im Vordergrund", "Eingabefeld im Fokus", "tippe den Prompt", then a tick. The rows cannot be clicked, never take focus and are left out of every screenshot. The Desk page sends them as `{"type":"activity","id","phase":"thinking|heard|start|done|fail","label","tool","ms","reason"}`; a message that cannot be read is dropped and logged as `activity.invalid` with the field that was wrong. Config `ActivityOverlay` (`true` by default; `false` = no rows).
- **Screenshot feedback.** When the agent looks at the screen for a reason you can see (session start, "schau auf den Bildschirm", a Caps highlight) the captured monitor gets a faint purple flash (12 % at most, 180 ms) and a 220 px thumbnail of exactly that picture appears bottom right and fades out over about 1.4 s. It is drawn after the capture by a window that Windows leaves out of captures, so it can never be part of a frame; the thumbnail lives in memory only. At most one flash per 2 s. Config `ScreenshotFeedback`: `"visible"` (default: start, on request, highlight), `"all"` (every frame that is sent, including the routine ones), `"off"`. The log line is `screen.feedback {reason, shown}`.
- **Sitzung startet ….** The first session after launch can take seconds (the Desk's browser and page are still starting, the microphone is opened). The note says "Sitzung startet …" at once and counts seconds after the third; only after 15 s without voice does it turn into the orange "Desk-Stimme startet nicht". The log has `session.startup {phase, ms}` for the app's own start (`app-environment`, `app-controller`, `app-page`) and, per session, `hotkey`, `browser-ready`, `page-session`, `voice-request`, `voice-unacked`, `voice-on` (ms counted from the key press). The web-session cookie is now fetched while WebView2 starts instead of after it.
- **The drawing window (v0.1.7).** It has a taskbar button. It comes to the front only the first time a diagram shows up by itself in this app run (never taking focus). If you minimise it, it stays minimised: new diagrams only update the page inside, nothing restores or flashes it, until you click its taskbar button (or use the tray / shortcut); the end of a voice session leaves a minimised panel where it is (`canvas.panel kept-minimized`), and the next session does not bring it back. A panel whose browser could not be created is hidden again and does not use up the one automatic "front", so the next diagram tries again. Closing it still keeps it closed until the next session, and the shortcut and tray entry always work. `canvas.panel {action, why}` records every change (and every ignored diagram with the reason).

## Computer control (v0.1.7, F)

**What it does.** On a spoken request ("übernimm den Rechner, öffne github.com und ...") the voice agent can operate your PC for a while: open and read Chrome tabs, click and type in them, and click and type in Windows apps you named (UI Automation, no screen guessing). A second model in the Desk proposes one action at a time; **this app decides.** The rules are compiled into the app (`ComputerPolicy`), not data from the Desk. It acts in your name with your logged-in accounts: read the lists below.

**Turn it on.** It is off. Tray menu **Computer-Steuerung erlauben** (a box explains the risks first); the switch is stored as `ComputerUse` in `config.json` and reported to the Desk (`POST api/device/computer`). Turning it off, or ending the voice session, stops any run. Your own extra sensitive sites go into `config.json` as `"ComputerSensitive": ["firma.example"]` (they only ever add to the lists below).

**Keys.** Ctrl+Win+Shift+**X** stops at once (keyboard hook, plus `RegisterHotKey` as a second path; **a run does not start unless one of the two is live**, and it ends if both die). Ctrl+Win+Shift+**Y** confirms an open question; pressing Ctrl, Win or Shift on the way there is not "you touched it". Touching any other key or the mouse pauses the run ("Du bist dran, sag z. B. „mach weiter“") and stops typing that is in flight; it goes on only after a real sentence of yours (not "ja", not noise). While a run exists a purple frame is drawn around every monitor and a banner shows your sentence, the step and "Strg+Win+Umschalt+X stoppt". The overlay is left out of every capture and is click-through; **over a remote desktop it may not show.**

**Scope.** A run may act only on what your own sentence names (a site such as `github.com`, a word such as "Gmail", "hier" as a whole word, an app such as "Editor"). "Google" means `www.google.com` only, not Gmail, Docs or Sites. Nothing named: it may only read, focus and scroll.

**Who can start it.** Only your own spoken sentence, and the sentence must read like an order ("Übernimm den Rechner", "Öffne gmail"), not a question, a doubt, a negation ("öffne die Mail nicht") or a report ("er übernimmt die Kosten"). **Starting a run with a scope, and every later extension, asks for the code or the chord once** (the question shows the goal; after an extension the banner shows the new goal), so a voice from a video cannot open or widen a run.

**Four kinds of action.** *Read* and *inside the scope*: it just does it. *Outside the scope*, on the sites and apps in the lists below (whatever the button says), Enter, delete or send-like labels, a link or form that leads to another origin, a browser it cannot see into, file dialogs, and **everything once the run has read a sensitive page or a server_read** (taint): **it asks.** The question is built by the app: what, where, the domain a link leads to, the path of an opened URL, for typing the text itself (at most 200 characters, longer R2 typing is refused), for forms every field including rich-text bodies and recipient chips, read live and quoted as page text; for Enter the focused field. It is shown on the overlay with a **2-digit code** (code first and large, then the whole text, wrapped) and read out by the voice. You say "ja, vier sieben" or press Ctrl+Win+Shift+Y. The code never goes to the Desk, the voice or any model and is not in the durable trace; it works once, for 60 s; **eight questions per run** (a Gmail send can take several: Compose, To, Subject, Body, Send), two unanswered ones end it, "nein" stops it. The voice may read the question with "punkt" for dots, in any case and with one short "Okay," in front; any other deviation voids the question. The action is bound to the exact element (tab, frame, page load, node, name, whole form content; for windows the element, process, window and position; for Enter the focused element): if anything changed in between it is dropped. Rich-text bodies and recipient chips of Gmail, X, Telegram, Slack, Discord and WhatsApp Web are read generically (contenteditable, `[email]` chips), **not with a reader per site: on those sites the question says that recipients or text may be incomplete.** *Refused, no question possible:* password managers, `chrome:`/`file:`/`data:`/`javascript:` pages, terminals and shells, Registry, Task Manager, Run dialog, Start search, the Explorer address bar, the Desk itself and this app's own windows, Win key chords and clipboard keys, any key outside Tab, arrows, Page up/down, Home, End, Esc, Ctrl+F (Enter asks, and only with a verified focused field). Text for typing may not contain newlines or other control characters (2000 characters at most, 200 when it asks) and never goes into a password field.

**Reading.** Password-type fields, one-time codes and card fields are never read; the sites, apps and file names below come back as "ausgeblendet", in addition to your own lists. Secret-looking values in anything returned (keys, tokens, JWTs, private-key blocks, `key=value` pairs, long hex or opaque strings) are replaced by "ausgeblendet" before they leave the app. Windows of a browser are read through Chrome only: the accessibility tree of a browser window is refused, and a screenshot is taken of one window (never the whole screen) only if it is a browser tab with a verified in-scope URL or a non-browser window that is not read-denied, and only if no other window lies over it. A tab outside the scope is neither listed nor read, **including a tab the run opened itself once its origin has left the scope** (redirect, `location=`, a link): it loses its refs. Page text is handed to the model as data, after the same redaction on the Desk.

## Main Agent prompt (v0.1.6)

**What it is.** The voice agent can hand a prepared prompt to this app. (Which spoken words make the agent do so is decided by the Desk, not by this app; this app only reacts to the command.) The app types it into the message box of the Claude Code extension in **VS Code Insiders** (plain "Code" only with `MainAgentAllowStableCode: true` in the config and when no Insiders window exists; without it and without an Insiders window the answer is `no-window`) and stops there: **it never presses Enter to send**, you read it and send it yourself. The Desk sends the text over the command channel (`…/commands`, the same long poll as "look at the screen"); the app answers `received` at once and `done`/`failed` with a code (`typed`, `typed-unverified`, `no-window`, `no-foreground`, `no-field`, `wrong-focus`, `interrupted`, `busy`, `no-session`), whether it landed and how many characters; the text itself never goes back and is not in the log or the trace.

**What it does, in order.** (1) Looks at the top-level VS Code Insiders windows (most recently used first; a title with `[WSL` goes first, but it is not required). Windows on another virtual desktop are skipped, and so are the auxiliary windows of the same process whose title starts with "Developer Tools", "Issue Reporter" or "Process Explorer". (2) Searches each for the Claude message box through UI Automation (accessible name from `MainAgentInputNames`, about 2.5 s per window); the first window that has one is the one with an open Claude session, otherwise the most recent window is used and the command palette opens the box. (3) Brings that window forward (restores a minimized one and keeps it maximized), without waiting for or touching the mouse; if a modifier key is held it waits up to 2 s and then answers `busy`. (4) Puts the keyboard focus in the box: directly through UI Automation, or with Ctrl+Shift+P, "Claude Code: Focus input", Enter. That Enter is the only unshifted Enter of the feature and is sent only while the palette has the focus **and** UI Automation shows the selected list entry with a name containing "Claude Code: Focus input" (an extension that is disabled or renamed shows another entry or none: then nothing is run, Esc closes the palette and the answer is `no-field`). Esc is sent only while the palette has the focus at that moment, never into a terminal. (5) **Checks before the first character**: the focused element belongs to that VS Code process, is named like the message box and has no ancestor whose class contains `monaco-editor`, `xterm` or `terminal`. (6) Types with Unicode key events (umlauts, emoji, `#`), 24 characters at a time; a line break is Shift+Enter; a `/` or `@` at the start of the text or of any line gets a space in front because the extension would open a menu (a mid-line `@` is typed as it is and may open the file menu). Existing draft text stays: it adds a space after it. Before every batch it checks that VS Code is still in front, no key of yours is held and the box it verified still has the keyboard focus (one call); the first batch and every 300 characters repeat the full check including the ancestors, and the check is repeated right before the Ctrl+End that moves the caret behind a draft. The remaining gap is one batch of 24 characters between check and keys. Reading the draft has a 1 s budget; a draft that cannot be read counts as a draft (one separator space is typed). The whole run has a hard 30 s deadline from receipt and never starts typing with less than 8 s left (`interrupted`); while a prompt runs, the drawing panel stays closed (it opens afterwards) and a dictation waits to be injected, and a prompt that arrives while a dictation is being injected waits up to 3 s, then answers `busy`. If a prompt stops with `interrupted`, the window with the text says how many characters are already in the box. Pressed modifier keys (Alt, Ctrl, Shift) are always released again, also when Windows refuses the input. a key press of yours in between ends the typing (`interrupted`) and leaves what was typed. (7) Reads the box back and checks again half a second later that the text is still there.

**What it refuses.** If any check fails nothing is typed and the answer is `failed` with the code; a small topmost window "Nicht eingetippt: <Grund>" shows the text with **Kopieren** and **Schließen** (it never takes the focus and is left out of screen captures). **The clipboard is never used**; only the Kopieren button puts the text there. The text is never typed into an editor buffer or a terminal: the check in (5) is the gate. One prompt at a time (a second one is answered `busy`), a repeated command id is ignored, text is capped at 8000 characters, tabs become two spaces and other control characters are dropped.

**Side effect to know.** Finding the box uses UI Automation, which switches on Chromium's accessibility mode in the VS Code process for as long as it runs; VS Code can become a little slower. It is the price of reading the box instead of guessing.

**What is proven and what is not.** `ci/main-agent-e2e.ps1` (workflow *VS Code Main Agent prompt*) downloads the real VS Code Insiders archive, installs the real `anthropic.claude-code` extension and runs the feature on a Windows runner: VS Code behind Notepad, minimized (and maximized again), Claude panel closed (palette route), focus in the editor buffer, focus in the integrated terminal, two Insiders windows of which only the older has a Claude session, the fail-closed case with the fallback window, a draft that stays, and a palette whose top entry is not "Claude Code: Focus input" (nothing runs, nothing is typed, the palette is closed again). Every scenario is judged afterwards through UI Automation (the box holds the text, still holds it 3 s later, the clipboard sequence number is unchanged) and leaves a screenshot. **Not proven:** your WSL remote window (the runner has no WSL window; the `[WSL` title is only used for ordering), your extension version (the runner installs the current marketplace version, 2.1.316 at the time of writing), non-English VS Code (the message box name comes from the extension and is configurable), and anything with a screen reader or accessibility flags changed. The test runs elevated; elevated VS Code with a non-elevated Screen Agent cannot be typed into (Windows blocks the keys: `interrupted`).

## Drawing panel (v0.1.6)

A small window "Screen Agent · Zeichnung" (default 440×340, resizable, minimum 320×240, always on top, no taskbar button) shows the board the voice agent draws on (the Desk page `/?panel=canvas`, same sign-in as the Desk window). It opens by itself when the agent has something on the board (config `CanvasPanel`: `"auto"`; `"manual"` = only on request), with Ctrl+Win+Shift+D (session only, like mute), from the tray (**Zeichnung zeigen**) or from the button on the Desk page. Closing it hides it and it **stays closed until you open it or the next voice session starts**; at the end of a session it goes away. It opens without taking the focus. Position: where you moved it last (if that spot is still on a monitor), otherwise bottom right of a monitor that does not hold the window you are working in (else bottom right of the current monitor), above the status note and clear of the taskbar.

The panel is left out of every screen capture (display affinity 0x11), otherwise the agent would see its own drawing. Windows has to confirm that setting when it is read back; if it does not, the panel is never opened (not even by the chord) and the note says so once.

## Screen vision (v0.1.5)

While a voice session runs the app sends the Desk one frame at session start, then every `IntervalMs` (4 s) and at once when the foreground window changes, but only when the picture changed or when the voice agent asks for a fresh look (long poll `…/commands`; a fresh look is always captured and sent at once). "Changed" is a finer test than before: the screen is reduced to a 320×180 grey grid, a pixel counts when it moved by more than 20 levels, and the picture counts as changed when any 20×20 patch of the grid has 8 such pixels. A new 5-digit number in a corner counts, a blinking caret does not. The comparison is always against the last frame the Desk accepted: a frame that was skipped, failed, rejected or rate-limited never becomes the reference. A frame is a JPEG of at most 1600 px width and 300 KB, kept in memory only, never written or logged.

**Which providers receive what.** The frame goes to the Desk gateway, which has Google Gemini describe it (and the marks you draw); Gemini is the only provider that receives images. The voice provider you chose (xAI Grok, OpenAI or Google) receives only the text description and the a# ids, never the image. Nothing is stored: images exist in memory only and are not logged. Screen capture happens only while a session is running and not paused, and the small note shows that.

A locked screen, the sign-in screen and a UAC prompt (the secure desktop) yield no frame; the note says "Bildschirm gesperrt" and the agent is told the screen is locked. Every other skipped frame has a reason in the log (`screen.frame` decision `skipped`, `why`: `locked`, `config-list`, `capture-failed`, `windows-changed`, `rejected`) and is simply tried again at the next tick. The Start menu, Alt-Tab and the like are ordinary windows. In the log, unchanged frames appear as one `deduped` line per run of unchanged frames, then one every 30 seconds.

The a# ids are read in the background (OCR on the native, full-resolution picture) and posted when ready; they never delay the frame. The Desk's vision model also lists the ids it reads on the picture; those the registry confirms are added to the ids shown in the note. A 409 from the Desk ends the frame loop until the next dialog. The Desk does the vision processing (see the gateway).

**What is kept.** Images: nothing, anywhere; they live in memory for one request. The app's own log has no text at all. The Desk session trace (30 days, for debugging) keeps what was said in the session, including numbers the agent reads aloud, plus the start of each screen description and of each marking with digits replaced by `#`.

## Logs

Hotkey events, frame decisions (sent, deduped, skipped and why), OCR timings (`screen.ocr`: ms, engine, counts), highlights (`screen.highlight`: ok, why, ms, bytes), ids seen, app version and session lifecycle go to a small rolling file `%LOCALAPPDATA%\ScreenAgent\logs\screenagent.log` (two files, 2 MB each) and in batches every five seconds to the Desk session trace (`POST /api/device/session/<sid>/trace`, best effort; set `TraceUpload` to false to stop). Neither contains images, OCR text, window titles or transcripts. Failed/unknown candidates are never forwarded. Unchanged frames renew the same confirmed IDs every 30 seconds. Frame versions use monotonic Unix milliseconds. Pause, stop, a locked screen and errors clear Desk context and companion chips (the Desk is told which: `locked`, `paused`, `stop` or `error`). Failed validation clears IDs immediately; network/409 failures retry with exponential backoff capped at 30 seconds and a warning note.

**Errors are always explained (v0.1.7).** Everything the user sees has a log line with the reason: `ui.notice {msg, level, why, exType}` (every toast, one code path; a warning without a `why` is refused by the test), `ui.balloon`, `ui.window` (message boxes, the dictation and prompt windows, the Desk text on a WebView2 failure), `ui.status` (status line level changes), `ui.pairing` (pairing errors). Every caught exception is `app.error {stage, exType, msg, hr}` (message redacted and capped at 120 characters; the same stage repeats at most every 10 s with a `suppressed` count) or carries a one-line comment why silence is right. Failed Desk calls are `http.fail {route, method, status, ms, sent, got}` (route without ids). Also: `webview.process.failed`, `nav.fail`, `nav.blocked`, `voice.ack.fail`, `mute.ack.fail`, `hook.install`, `inject.refused {why}` (target-changed, elevated, focus-changed, password, blocked-window, locked-host, modifiers-down, prompt-busy), `frame.encode.fail`, `highlight.build.fail`, `telemetry.flush.fail` (local only). Unhandled exceptions are written to the log (and the queue file) before the process dies; the next start ships the queue. Each upload batch starts with `client.batch {app, commit, session, n, dropped}` and carries `app`, `commit`, `session` as top-level fields. `tests/ScreenAgent.Tests/ErrorsLoggedTests.cs` scans the source for these rules.

## Start briefing (v0.1.7)

When a session starts, and whenever the voice agent asks for a refresh (`current_state`), the app sends the Desk a short overview of the laptop: `POST api/device/session/<sid>/briefing` with `{windows, tabs, mainSession, screenText, commandId?}`. It runs on background threads inside a 1.5 s budget, never on the UI thread, and a failure never touches the session. Set `Briefing` to false in `config.json` to switch it off.

- **windows**: visible top-level windows (process, title) in z-order, at most 30. Tool windows, windows on other virtual desktops and the app's own windows are left out. Windows that match your `BlockProcesses` / `BlockTitlePatterns` are left out too.
- **tabs**: Chrome tabs, at most 40, read through UI Automation only (the tab strip of each Chrome window; the address of the selected tab from the address bar, without query and fragment). No debugging port is used, so Chrome shows no remote-debugging dialog. Reading the tab strip makes Chrome switch its accessibility support on, as for any screen reader.
- **screenText**: what OCR read in the last frame, 1500 characters at most, never an image. It is dropped with the picture (pause, lock, end of session) and only kept for a picture that is still current. The start briefing waits up to 1.5 s (alongside the other sources) for the first OCR result of the session.
- **mainSession**: the last 12 user/assistant text messages (300 characters each, no tool output) of the newest Claude Code transcript. Default `\\wsl.localhost\Ubuntu\home\flori`: the app lists `.claude*\projects\*` for `*.jsonl` (directory listings only, never a recursive walk), looks into the 8 most recently changed project folders per account, takes the newest file by modified time (what was found is kept when the time budget runs out), seeks to its last 512 kB at most and streams it line by line (about 1 MB working budget, nothing read whole, an unparsable first line is skipped). `MainSessionPath` overrides the place: a `.jsonl` file, a projects folder, an account folder or a home folder. For a `\\wsl.localhost` path the app first asks `wsl.exe -l --running` and sends nothing for this block if the distro is not running (opening the share would start it). A share that stalls is abandoned after the budget.
- Everything is run through a local secret filter (`sk-`, Stripe `sk_live_`/`rk_live_`, `ghp_`, Google `AIza…`, Hugging Face `hf_…`, Telegram bot tokens, bearer and Basic authorisation, JWTs, PEM private keys, `key=value` and "password is …" secrets, long hex runs and mixed-case base64-like runs of 32+ characters); the gateway filters again.

The log gets `briefing.collect {windows, tabs, messages, bytes, ms, tailBytes, missing:[...]}`, `briefing.sent {status, attempts, ...}` and `briefing.fail {stage, reason}`: counts and reasons, never contents. `missing` names what is absent and why (`main-session:wsl-not-running`, `main-session:path-missing`, `tabs:none`, `tabs:timeout`, ...). A 409 from the Desk (its session is not live yet) is retried after 1.5, 3 and 6 seconds. A source whose thread is stuck (a stalled share, `wsl.exe`) is not started a second time until it returns (`missing: …:busy`), and a refresh the app has to refuse as busy is still answered, with an empty body that carries the `commandId`.

## Dictation and learning

The native WASAPI recorder produces 16 kHz, 16-bit mono WAV, written to disk from the first sample (v0.1.7, next section). During a Desk session it requires a mic-mute acknowledgement within 500 ms before recording; after completion/discard it requests acknowledged unmute and retries every two seconds while the note shows **Desk-Mikro stumm**. Capture is independent of pending transcription; immutable clips are transcribed and inserted in recording order. Dictation sends the process, at most 500 preceding field characters, visible confirmed IDs and dictionary terms. The Desk reconciles Groq/OpenAI/Google transcripts. Google processes highlight images; Desk voice uses the chosen voice provider. No vendor credentials are stored in this app.

Target HWND is captured at chord key-down. UIA binding happens on the UI thread and refuses a changed HWND. Before insertion the app waits for modifiers up and revalidates HWND, UIA element, password status and elevation. A changed or unsafe target gets **no** clipboard copy and nothing typed: the text goes to a window that stays until you close it (see below). Short text and terminal targets use Unicode SendInput; long non-terminal text uses clipboard paste, restoring the clipboard after 400 ms only if its sequence is still ours; when another program holds the clipboard (a clipboard manager, RDP) the text is typed instead. All newlines become spaces and controls are stripped; Enter is never sent. Spoken newline commands are not interpreted in this preview.

Correction learning excludes terminals, password fields, unreadable fields and ambiguous insertion spans. It polls the same safe UIA target for at most 45 seconds, requires a stable 1–3-word letters-only replacement, counts at most once per independent insertion, and promotes on the second sighting. Pending pairs survive restarts at `%APPDATA%\ScreenAgent\learn-pending.json`. A failed promotion retains the pair. Open Desk **/device** to inspect the learned-term list and delete a term; verify that it disappears from subsequent dictionary results.

## Dictation: recordings, long dictations, captions (v0.1.7)

**Your words are never lost.** Every dictation is written to `%LOCALAPPDATA%\ScreenAgent\dictation\<yyyyMMdd-HHmmss>-<id>.wav` from the first sample, before anything else happens to it. The WAV header is fixed up every 3 seconds (and the file flushed to disk), so a crash or power loss leaves a playable file; at the next start the app repairs leftover files and offers them as failed dictations. Next to each wav sits `<same name>.json` (state, reason, process name, length, file list; for a failed dictation also the live-caption text so you can copy it; nothing is uploaded from it). If the disk refuses the write, recording continues in memory and the note says so. There is no length limit; after `DictationMaxMinutes` (default 60) the app tells you and starts the next file (`…-p2.wav`), the recording goes on.

**Long dictations.** A dictation under 55 s is one request, as always. Longer ones are cut by the app at a pause (RMS over 30 ms frames, adapted to the room; the first pause of 300 ms or more after 20 s, so chunks go out while you still talk) or, with no pause by 55 s, hard at 55 s with 0.5 s overlap that the join removes again by word overlap. Chunks go one at a time, in the background, with 2 retries (1 s, 3 s) for timeouts, 429 and 5xx; a lost connection does not use retries, it waits and goes on (10 min while you talk, 45 s after you stopped). At the end the app waits for the last chunk, joins the texts and inserts once. The note shows “Diktat · 3:12 · 4/5 fertig”. A chunk that stays failed is replaced by its part of the live caption text (if captions run) and the result gets the notice “Teil aus Live-Text”; the file stays as a failed dictation. Each request sends `chunk` `{dictationId,index,final}` and the tail of the text so far in `fieldBefore`.

**What you see when something fails.** Never a silent loss: a notice “Diktat nicht verarbeitet: <Grund> · <Dateipfad>” and a small window (topmost, never takes the focus, left out of screen captures) with the reason, the path and the buttons **Erneut versuchen**, **Ordner öffnen**, **Text kopieren** (only when a partial or caption text exists) and **Schließen**. The tray menu lists every failed dictation that is still on disk (“Diktat vom 10:37 (3:13) wiederholen”), also after a restart. **The text is never put on the clipboard behind your back and never typed into a field you did not choose** (this settles the earlier question: the no-clipboard rule covers dictation for this path). A first pass types into the field you dictated into only while that field is still the focused, safe one; short dictations into the same field go in as ever. If it is not (you clicked elsewhere while a long dictation was being transcribed, the field is protected, typing threw an error), and for **every retry**, the text appears in a window (`ui.window dictation-result`) with **In aktuelles Feld einfügen** (types into whatever field has the cursor *now*, only when you click it; the window never takes the focus), **Text kopieren** and **Schließen**. Until you close that window the dictation stays `failed / undelivered` with the text in the sidecar: the tray still offers it (and shows the stored text again without a new transcription), and a restart does not lose it. Closing the window, or inserting from it, marks the dictation done. A retry of a dictation whose partial text was already inserted shows the full text the same way. If the window cannot be proven out of screen captures, it shows no text at all, only the buttons. A recording shorter than 300 ms or digital silence makes no provider call (log `dictation.skip`, small notice). Ending or changing the Desk session while you dictate does not drop the recording; only the discard chord does, and that keeps the file 24 h too. While you dictate the mute key does not unmute the voice microphone (“Mikro bleibt stumm während des Diktats”). Pause ends a dictation like a stop: its text is still delivered (the notice says so).

**When the microphone goes away mid-dictation** (unplugged, device switched, driver reset) the status shows “Mikrofon getrennt”, a window stays up until closed, and the app tries to open the default microphone again into the same recording (`dictation.capture.lost`, `dictation.capture.restart {ok}`); what was said in the gap is missing. If it cannot be reopened, stopping the dictation inserts the text so far and leaves the dictation `failed` with stage `capture` and the reason, so it is never mistaken for a complete one. Capture itself only copies each block into a 5-minute queue; a writer does the disk write, fsync and logging, so a slow disk or virus scan cannot drop samples. Audio that still goes missing (wall clock against samples, or a full queue) is logged as `dictation.gap {missingSeconds, at, dropped}`.

**Empty answers are failures.** A 2xx reply without a `text` string (a captive portal's page, a cut-off body) is a failed chunk with code `bad-reply`; an empty text for a chunk with speech (over 2 s, peak above 2000) is a failed chunk too (`empty-text`, asked once more). A whole dictation that comes back empty although there was speech ends `failed`, with a retry, never `done`. When the disk refused and a transcription fails, what only reached memory is written to a file (the dictation folder, else `%TEMP%\ScreenAgent-dictation`; `dictation.dump`) and the memory is kept for the retry of this run.

**Retention (local only).** After a successful dictation the wav is kept `DictationKeepHours` (24); a failed one `DictationKeepFailedDays` (14); everything together at most `DictationCapMb` (2048), oldest successful first. A failed file younger than 14 days is never deleted, not even over the cap. Swept hourly (the first sweep 10 minutes after start, never in the start that announces what a crash left); a recording recovered at start counts its age from the recovery. Nothing leaves the machine except the chunks sent for transcription.

**Captions (`Captions`: `"dictation+voice"` default, `"dictation"`, `"off"`).** While you dictate, and in a voice session (a second WASAPI shared capture in parallel), every 1.5 s while the recent audio shows speech the last 6 s go to `/api/device/caption`. A subtitle line shows at the bottom centre of the monitor with the active window: one or two lines in a dark translucent pill, click-through, no focus, left out of captures, gone 3 s after the last speech. Answers that arrive out of order are dropped; the texts of the rolling windows are stitched by word overlap so the line grows and only its last words change. Every dictation has its **own** live text, fed while it is live and for 4 s after it ended, so the fallback for a failed chunk is never what you said to the agent afterwards or in the next dictation; the cut points are word positions and approximate (captions lag the audio by 1.5–3 s, so a chunk's slice can be shifted by a few words). If the subtitle microphone cannot be opened (held by another program) it is tried again every 30 s, not every tick (`caption.error stage=tap`). A mute from the Desk page stops it within 250 ms (the page may also send `{type:"mic-state",muted}`). The subtitle and activity windows are not shown unless Windows confirms the capture exclusion by reading it back (`capture.exclusion-failed {window}`, once). At most one request in flight; 5 failures in a row pause captions for 60 s; a 429 or 503 hides them for the session (one log line `caption.off`). Silence sends nothing. The text of captions is never logged; `caption.stats` (about every 60 s and at the end) carries counts, latency and the cost the Desk reports (target: about USD 0.40 per hour of speech, `usdPerSpeechHour`).

**Logs.** `dictation.start` (process, session), `dictation.cut`, `dictation.chunk` (index, bytes, seconds, ms, status, attempt, providers, code), `dictation.done` (seconds, chunks, ms, chars, degraded), `dictation.fail` (stage, reason, exception type, http status, path, bytes, seconds), `dictation.skip`, `dictation.discard` (why), `dictation.retry`, `dictation.refused` (why a start was refused), `dictation.disk`, `dictation.limit`, `dictation.recover`, `dictation.sweep`, `dictation.undelivered {why, chars}`, `dictation.insert {ok}`, `dictation.capture.lost`, `dictation.capture.restart`, `dictation.gap`, `dictation.dump`, `tick.error {where}`, `capture.exclusion-failed`, `caption.stats`, `caption.error`. File paths appear; audio and text never do. Client events now also reach the Desk without a session: a session trace when one exists, otherwise `POST api/device/log` (device log); they wait in `%LOCALAPPDATA%\ScreenAgent\logs\trace-queue.jsonl` (at most 1000 events, 24 h) until the Desk has taken them.

## What is captured, and the optional exclusion lists

Nothing is excluded by default: while a session runs, the screen you see is the screen the agent sees, including any window. What is not optional: capture only during an active, unpaused session; the visible note and tray state; images in memory only; the lock screen and secure desktop give no frame; dictation never types into password fields or elevated windows. The app's own windows are left out of every capture (they request WDA_EXCLUDEFROMCAPTURE).

If you want windows left out, put them in `BlockProcesses` (process name prefixes), `BlockDomains` (browser address host names) or `BlockTitlePatterns` (regular expressions on the window title) in `config.json`. All three are **empty by default**; while they are empty the app does not enumerate windows or read browser addresses per frame at all, it only looks at the foreground window's process, title and address for the frame. With entries, a matching foreground window is not captured (the note says "Fenster ausgenommen (Liste)") and matching windows behind it are painted black before anything is sent. An unreadable browser address never matches. Config files from v0.1.2 to v0.1.4 that contain `IdsOnlyDomains` are read without error; the key is ignored.

`%APPDATA%\ScreenAgent\config.json` is created on first run. Fields: `DeskUrl` (HTTPS origin), `IntervalMs` (1000–60000), `BlockProcesses`, `BlockDomains`, `BlockTitlePatterns` (all three empty by default), `VoiceProvider`, `Hotkeys`, `Indicator`, `SendFrames` (true; false = ids only, no images), `TraceUpload` (true), `RetainScreenshots` (false), `UserEmail` (optional local only), `CanvasPanel` (`"auto"` default, or `"manual"`: the drawing panel opens only on request), `MainAgentInputNames` (default `["Message input"]`: the accessible names accepted for the Claude Code message box), `MainAgentAllowStableCode` (`false` default: plain stable "Code" is never a target), `DictationMaxMinutes` (60), `DictationKeepHours` (24), `DictationKeepFailedDays` (14), `DictationCapMb` (2048), `Captions` (`"dictation+voice"`, `"dictation"` or `"off"`). `Indicator` is `"session"` (default: the small note while a session runs, plus short notices) or `"notices"` (only short notices; rely on the tray icon). Invalid configuration stops startup. The default chords are `session` Ctrl+Win+Shift, `mute` Ctrl+Win+Shift+M, `pause` Ctrl+Win+Shift+P, `dictation` Alt+Win (hold), `dictationToggle` Alt+Win+Shift, `handsFree` Alt+Win+Y, `draw` Caps, `canvas` Ctrl+Win+Shift+D. `session` and `dictationToggle` are three distinct modifiers (Ctrl, Alt, Win, Shift) and must differ; `dictation` is two of Ctrl/Alt/Win (the app warns at start if you pick Ctrl+Win, which belongs to Wispr); `mute`, `pause`, `canvas` and `handsFree` are two to four modifiers plus one action key. Missing keys take their defaults; if the default `canvas` chord collides with your own keys it moves to the first free letter of D, Z, G, J, K, or is dropped (the tray menu still opens the panel) and the trace says so, instead of stopping the app. Draw, mute, pause, canvas and hands-free action keys must differ and may be Caps, Space, A–Z or F1–F12. Invalid maps fail closed. `VoiceProvider` is passed to the companion page as its voice preference. Screenshot retention is disabled even if requested in config; the preview never writes captures to disk. UserEmail never enters API payloads. Also: `ActivityOverlay` (`true` default: the live rows above) `ScreenshotFeedback` (`"visible"` default, `"all"` or `"off"`: flash and thumbnail when the agent looks at the screen). `Indicator` is `"session"` (default: the small note while a session runs, plus short notices) or `"notices"` (only short notices; rely on the tray icon). Invalid configuration stops startup. The default chords are `session` Ctrl+Win+Shift, `mute` Ctrl+Win+Shift+M, `pause` Ctrl+Win+Shift+P, `dictation` Alt+Win (hold) `Briefing` (true), `MainSessionPath` (optional).

Live and file OCR prefer Windows.Media.Ocr and fall back to bundled Tesseract eng+deu. The memory path never writes a temporary screenshot. Native OCR DLLs are embedded, extracted with SHA256 verification into local AppData, and loaded through an explicit search path. Tesseract 5.2.0 and pinned tessdata_fast 4.1.0 are Apache-2.0; NAudio 2.2.1 is MIT; WebView2 1.0.2903.40 uses Microsoft's license.

## Verification and manual checklist

Windows CI builds, runs pure xUnit tests (shared OCR vectors, hotkeys, exclusion lists, change test and frame planner, correction diff/promotion/span, payloads, config, window placement at 100–200 % scaling, status texts, voice-start logic), publishes a self-contained exe, renders synthetic OCR fixtures at 24/36/48 px, forces the in-memory Tesseract fallback at all three sizes, and runs overlay/insertion selftests, and `--selftest-dictation` (the real recorder, chunker and chunk job against a stand-in Desk, fed from `testdata/e2e-actions.wav`: chunks, 503 retry, crash-copy repair, failure and retry from the file, retention, failure window and subtitle window flags). Since 0.1.2 it also checks that the exe is a GUI-subsystem program (no console window), that Ctrl+Win and Ctrl+Win+Alt pass through a real low-level keyboard hook untouched, that Ctrl+Win+Shift starts and ends the session exactly once in all six key orders with one mask key and no Start menu, that Alt+Win+Shift toggles dictation, Alt+Win hold still dictates and Ctrl+Win+Shift+M mutes only inside a session (`--selftest-hotkeys`; GitHub's `windows-latest` has an input desktop and runs it, a runner without one skips with exit 2 and the manual checklist applies), and that the Desk window starts hidden, is not topmost, opens, minimises, remembers its size, and that the status note is small, bottom-right, click-through and hides again (`--selftest-windows`). Since 0.1.3 the browser is hosted directly in the native client rectangle in device pixels, with bounds refreshed on open,
resize, monitor DPI change and rasterization-scale change; there is no temporary 400×300 WPF WebView layout.
Runtimes that cannot initialize an invisible parent get one bounded off-screen/no-activate tool-window show after six
seconds, hidden again when initialization settles (at most fifteen seconds later). This never appears in the taskbar
or on the monitor; opening Desk during startup cancels the off-screen state and keeps the user's ordinary window open.
The default Desk size is 900×800 DIP, clamped to the monitor work area. Windows selftests capture the real native WebView
at 100/125/150% rasterization (`artifacts/desk-controller-100.png`, `-125.png`, `-150.png`) and assert the DOM viewport in
physical pixels equals the entire native client rectangle after resizing and reopening. They also exercise pending and
completed pairing HTTP responses, DPAPI save/restore, a separate WebView cookie store, and credential-free request URLs.
